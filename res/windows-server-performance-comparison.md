# Windows Server 版本性能对比报告

## 背景

在同一腾讯云主机上分别安装 **Windows Server 2016 / 2022 / 2025**，硬件配置完全相同（2C2G），运行相同的性能测试脚本，对比浏览器模式和请求模式下的性能差异。

- 测试日期：2026-07-28（2022/2025），2026-07-22（2016）
- 浏览器模式数据源：`browser-jp`
- 请求模式数据源：`request-jp`
- 报告生成时间：2026-07-29

---

## 核心结论

1. **浏览器模式**：WS2016 性能是 WS2022/2025 的 **2-3 倍**，WS2022 与 WS2025 几乎没有差异
2. **请求模式**：三个版本性能接近（差距 <20%），说明问题仅存在于浏览器/Selenium/Chrome 路径
3. **根因**：新版本 Windows 默认安全机制（Defender 实时扫描 + 内核级进程缓解措施）严重拖慢 Chrome 高频文件 I/O 和子进程创建
4. **Defender 验证**：关闭 Windows Defender 实时保护后，WS2022 B5 从 3.8 → 4.2 tpm（+10.5%），WS2025 B5 从 3.7 → 4.8 tpm（+30%），确认 Defender 是主要因素之一

## 磁盘 I/O 对比

采集的 perf 数据中包含 `disk_read_bps` / `disk_write_bps`，对比浏览器活跃期间（`browser_proc_count > 0`）的磁盘读 I/O：

| 指标 | WS2016 | WS2022 | WS2025 |
|------|:------:|:------:|:------:|
| disk_read avg (MB/s) | **2.8** | 14.7 (5×) | 10.1 (3.6×) |
| disk_read p50 (MB/s) | **0.0** | 0.8 | 0.4 |
| disk_read p95 (MB/s) | **17.1** | 51.6 (3×) | 48.2 (2.8×) |
| disk_read max (MB/s) | 97.4 | 558.3 | 435.8 |
| disk_write avg (MB/s) | 0.8 | 1.2 | 1.1 |

**关键发现**：
- WS2016 浏览器活跃期间 **p50 磁盘读为 0**（一半时间无需读盘），而 WS2022/2025 持续有读 I/O
- WS2022 磁盘读 avg 是 WS2016 的 **5 倍**，p95 尖峰是 **3 倍**
- 这正是 Windows Defender 实时扫描的特征：Chrome 每读取/写入一个文件，Defender 拦截扫描一次

---

## 根因分析

### 主因：Windows Defender 实时扫描

**验证方式**：关闭 Defender 实时保护后跑 B5 对比：

| 版本 | 关闭前 tpm | 关闭后 tpm | 提升 |
|------|:------:|:------:|:----:|
| WS2022 | 3.8 | **4.2** | +10.5% |
| WS2025 | 3.7 | **4.8** | +30% |

关闭后仍未达到 WS2016 的 7.5 tpm，说明 Defender 并非唯一因素。WS2025 关闭后提升幅度（30%）远大于 WS2022（10.5%），暗示 WS2025 上 Defender 的扫描开销比 WS2022 更重。

```powershell
# 临时关闭（验证用）
Set-MpPreference -DisableRealtimeMonitoring $true

# 恢复
Set-MpPreference -DisableRealtimeMonitoring $false
```

**触发机制**：Chrome 在浏览器模式下大量读写文件（user-data-dir、disk-cache、temp），每次文件操作都被 Defender 实时扫描引擎拦截。请求模式不走 Chrome 文件 I/O，因此不受影响。

### 次因：进程级安全缓解措施

WS2016 没有 `Get-ProcessMitigation` 命令（PowerShell 安全模块 5.1+），表明其进程安全框架本身比 2022/2025 少得多。Microsoft 在 2016→2022 之间默认开启了多项内核级进程缓解：

- **Control Flow Guard (CFG)**：每次 Chrome 子进程内部的间接跳转都要经过 CFG 校验
- **Code Integrity (CI) Policy**：WS2025 上 `DeviceGuardCodeIntegrityPolicyEnforcementStatus=EnforcementMode`
- **其他**：ASLR 强度提升、内核 CET 等

Chrome 是典型的多进程应用——B5 产生 20-62 个子进程，每个进程的创建、IPC 通信、文件 I/O 都要经过这些安全层检查，累积成显著的吞吐量退化。

## 各版本系统安全配置对比

| 检查项 | WS2016 | WS2022 | WS2025 |
|--------|:------:|:------:|:------:|
| Windows Defender 实时保护 | 开启 | 开启 | 开启 |
| Get-ProcessMitigation 命令 | ❌ 不存在 | ✅ 可用 | ✅ 可用 |
| VBS / HVCI | — | 关闭 | 关闭 |
| Device Guard Code Integrity | — | 关闭 | EnforcementMode |
| CFG | 默认低 | 默认高 | 默认高 |

## 建议

1. **生产环境选择**：如果业务场景以浏览器爬虫为主，WS2016 性能优势显著（即使关闭 Defender 后 WS2025 的 4.8 tpm 仍低于 WS2016 默认的 7.5），建议优先使用
2. **WS2022/2025 优化**：关闭 Defender 实时保护是必做项（+10%~+30%），可额外排除 Chrome 的 user-data-dir、cache、temp 目录
3. **注意**：关闭 Defender + 进程缓解后 2022/2025 能否追平 2016 仍未知，如果差距主要来自 CFG/Code Integrity 等内核级安全策略，代码层面无法绕过
4. **Linux 对比**：腾讯云 Linux（同配置）浏览器 B5 tpm 4.4，也优于 WS2022/2025 默认值（3.7-3.8），是另一个可选方向
